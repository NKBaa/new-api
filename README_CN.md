## 一、一句话说明

我们在**官方 New API 原版**的基础上，加了 **12 项自己需要的功能**。

**关键点：只加功能，不改官方原有的东西。** 官方代码就像一栋楼，我们只是在里面加装了 12 件家具，没有拆墙、没有改结构。这样以后官方翻新大楼时，我们的装修很容易搬过去。

## 二、到底加了哪 12 项功能？

### 1. 充值返佣（推广分润）
**做什么**：用户 A 推荐了用户 B，B 充值时 A 能自动拿到一定比例的返佣。

**你会在哪看到**：个人中心 → 推广/返佣卡片，能看到自己拉了多少人、拿了多少返佣。

**怎么设置**：后台设置里填返佣比例（0~100%）。

**为什么可靠**：返佣和充值在**同一个数据库事务**里完成——要么都成功，要么都不发生。并且用数据库的唯一索引防止"同一笔充值被重复发佣"（网络重试、并发回调都不会重复发钱）。

---

### 2. 推荐计划说明文字可自定义
**做什么**：推荐页面那段说明文字，你可以自己在后台改，不用改代码。

**怎么设置**：后台填一段文字；不填就显示默认文案。

### 3. 普通用户看不到"模型被替换"的细节（防穿帮）
**做什么**：你在后台配置的模型映射（比如把便宜的模型伪装成贵的），**普通用户看不到真相**，只有管理员能看到完整信息。

**为什么重要**：这是商业保密需求——不能让用户发现"我买的是 A 模型，实际给我的是 B 模型"。

**注意**：管理员切换成"只看自己"的视图时，也会被当作普通用户对待（不会意外泄露）。

**做什么**：你可以给**所有用户**设一个统一的默认外观（深色/浅色、配色、圆角等）。

**用户自由度**：用户自己改了外观后，就固定用他自己的；用户点"重置"就回到你设的全站默认。

**新增**：导航栏圆角单独可调（6 档）。

**注意**：我们**没有**改官方的主题基础文件，只是"设定默认值"和"记录用户自己的选择"。

### 11. 伪 200 拦截与自动换渠道 ⭐（这项设计改过，请重点看）

**问题背景**：有些上游 AI 服务会"假装成功"——HTTP 状态码返回 **200（成功）**，但正文其实是一句拒绝语，比如：

> "The prompt could not be submitted. The prompt contains sensitive words that violate Google's Generative AI Prohibited Use policy."

如果不处理，用户会**花钱买到一个拒绝回答**。

**我们做什么**：识别出这种"假成功"，然后**自动换一个渠道重试**。重试成功用户拿到答案；全部失败则**退款**。

**重要：这项功能是"每个渠道单独设置"的**

- **一个渠道一个开关**——开哪个渠道就只对那个渠道生效
- **渠道之间互相独立**，互不影响
- **没有全局开关**（这是你明确要求的）

**怎么设置**：
1. 进入**渠道编辑**页面
2. 切到「**请求与响应**」标签
3. 找到「伪 200 异常检测」开关，打开
4. 打开后会自动出现**规则列表**（已填好 13 条内置规则），你可以**随便改**

**规则能改到什么程度**（这是最近新增的能力）：

| 你想要的 | 怎么做 |
|---|---|
| 看看默认规则长什么样 | 打开开关就自动显示了 |
| 加一条自己的规则 | 在末尾加一行 |
| 删掉某条内置规则 | 直接删掉那一行 |
| 改错了想复原 | 点「**恢复默认**」按钮 |
| 完全不管规则 | 清空文本框 = 自动用内置的 13 条 |

**规则怎么写**（每行一条）：

```
the prompt could not be submitted
the prompt contains sensitive words | violat, blocked, prohibited
```

- `|` **之前**：必须以它**开头**
- `|` **之后**：还必须**同时出现**其中一个词
- 词的**分隔符很宽松**：半角逗号 `,`、中文逗号 `，`、甚至再写一个 `|` 都认
- `#` 开头的行会被忽略（当注释用）

**为什么要求"以它开头"**：这是**防误判的关键**。如果只要求"出现这些词"，那么正常回答里只要提到这些词（比如你问"解释一下 Google 的政策"），就会被当成拦截 —— 实测会**100% 误判**。要求"开头就是拒绝语"才能准确区分。

**实测结果**：
- 正常内容（"解释 Google 的政策"、"翻译这句话"、"教程里引用这个报错"、"代码里写了这个字符串"）→ **全部不误判** ✅
- 真实上游拒绝 → **全部准确识别** ✅
- ⚠️ **但流式请求有一个已知不足**，见 [第六节第 4 条](#4-流式请求的一个已知不足如实说明)。

**不会误封渠道**：这里有一个"保险丝"——提示词被拦截**绝不会导致渠道被封**。即使你把这句报错文案填进"自动封禁关键词"里，渠道也不会被封（我们做了显式保护，不是靠巧合）。

### 12. OpenCode 渠道（新上游）

**问题背景**：OpenCode 这家上游只认"**它自己的官方客户端**"。你用普通方式去调它，它会直接拒绝，报错分别是：

- `400 MissingSessionID`（没带会话号）
- `403 Forbidden`（被识别成非官方客户端）
- `429 FreeUsageLimitError`（免费额度用不了）

**我们做什么**：给这套系统加了一个**新的渠道类型叫 OpenCode**。你在后台添加渠道时选它，它转发时会**自动把请求伪装成官方客户端发出的样子**（补齐官方客户端该带的那些请求头、会话号、请求号），上游就正常放行了。

**你要做的**：

1. 后台 → 渠道 → 添加渠道
2. 类型选「**OpenCode**」（图标已内置）
3. Base URL 默认就是 `https://opencode.ai/zen`，一般不用改
4. 填上 Key 即可

**几个你可能会问的**：

| 问题 | 回答 |
|---|---|
| 支持哪些模型？ | 后台可以在渠道里**拉取模型列表**（拉取时也会自动伪装，否则拉不到） |
| 我的客户端要改成什么协议？ | **不用改**，它完全兼容 OpenAI 格式，你原来怎么调就怎么调 |
| 我的客户端不支持流式怎么办？ | 没关系。上游只认流式，但**我们在中间帮你把它转回普通格式**，你这边收到的是正常 JSON |
| 会额外装什么东西吗？ | **不会**。没有新脚本、没有新后台进程，就是普通的一个渠道类型 |
| 会新建数据库字段吗？ | **不会**。渠道类型本来就有这一列，只是多了一个取值 |

**优先级说明**：如果你自己额外设置了「请求头覆盖」，**你的设置优先级最高**，会盖过我们的伪装头。所以不要手动覆盖那几个 `x-opencode-*` 头，否则可能又变成 403。

## 三、你最关心的三件事

### ✅ 1. 数据库不会被破坏

**没有**给官方已有的表加任何字段，**没有**执行任何改表操作。

唯一新增的是**一张独立的返佣流水表**（`affiliate_rewards`），用来记录"谁给谁返了多少佣"。这张表和官方表完全无关，官方升级时不会有任何冲突。

其他所有配置（开关、比例、文案）都存进官方原有的配置表里，**不需要改表结构**。

**为什么这很重要**：改表结构是最容易出事故的操作（数据丢失、升级失败）。我们完全避免了。

**没有** Python 脚本、**没有** Node.js 定时任务、**没有**需要单独启动的辅助程序。

- 部署简单（就一个容器）

**只改了 131 个业务文件**（其中 37 个是新增的），而且都是**必要的最小改动**。

我们**特意排除**了所有与业务无关的改动：

**为什么这很重要**：改动越少，以后官方更新时冲突越少，升级越省事。

### 3. 伪 200 检测的一个取舍

我们的判断方式是"**正文必须以拒绝语开头**"。好处是几乎不误判，代价是：如果某个上游把拒绝语放在**正文中间**（先输出一段前缀再拒绝），可能会**漏检**。

**解决办法**：遇到漏检时，在渠道的**规则列表**里加一行——因为规则是你自己写的，可以不受"必须以它开头"的限制。这正是规则可编辑的价值。

> 小提示：规则里的 `|` 之前要求"必须以它开头"。如果你要匹配"出现在中间"的内容，把它写成一个**更靠前的特征**，或者用下面的「自定义拦截特征」框（那个是**包含匹配**，不要求开头）。

### 4. 流式请求的一个已知不足（如实说明）

**先说结论**：用**非流式**方式调用（客户端不要求边生成边返回），伪 200 检测**一定命中**，不会漏。用**流式**方式调用时，只有当上游把整句拒绝语**一次性放在第一个数据包里**才拦得住。

如果上游把那句话**拆成好几个包**边生成边发，我们就拦不住——客户端会看到那句拒绝语，而且这次请求**照常扣费、也不会自动换渠道**。

我们实测了 6 种情况（同一句拦截语、检测已开启）：

| 上游怎么发 | 客户端怎么调 | 拦住了吗 | 客户端看到拒绝语了吗 |
|---|---|---|---|
| 整句一个包 | 流式 | ✅ 拦住（502） | 没有 |
| 整句一个包 | 非流式 | ✅ 拦住 | 没有 |
| 拆成 2 个包 | 流式 | ❌ **没拦住** | **看到了全句** |
| 拆成 2 个包 | 非流式 | ✅ 拦住 | 没有 |
| 逐词拆成 10 个包 | 流式 | ❌ 没拦住 | 没看到（每包都太短） |
| 逐词拆成 10 个包 | 非流式 | ✅ 拦住 | 没有 |

**为什么没修**：修它要改流式下发的时机（先攒几个包再决定发不发），会影响首包的响应速度。目前判断为"不值得为此改动核心链路"，所以**先如实记录，不动代码**。

**你现在能做什么**：如果遇到流式漏检，在渠道的「规则列表」里加一条**更靠前**的特征，或者用「追加特征」框（那个是**包含匹配**，不要求必须以它开头）。

> 注意：这一条是**实测发现**的，之前文档里"流式与首包探测"的说法容易让人以为流式也万无一失，现已改正。官方自带的回归测试只测了"整句一个包"这一种情况，所以测试全绿**不代表**跨包场景没问题。
